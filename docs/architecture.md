# Архитектура

Утверждены модульный монолит, Python/PySide6, SQLite/SQLCipher, SQLAlchemy/Alembic,
точные финансовые значения, Android на Kotlin и обмен независимых локальных баз.

## Реализованные слои

`domain` содержит сущности, типы денег и ошибки. Не импортирует Qt, SQLAlchemy,
SQLCipher или криптографию. `application/catalog.py` реализует сценарии справочников
через `CatalogRepository`. SQL и атомарная история находятся в адаптере
`infrastructure/persistence/catalog_repository.py`.

`application/vault.py` оркестрирует создание/открытие локальной книги, блокировку
и подключение адаптеров. На этом раннем этапе здесь же собираются начальные
метаданные книги; это не финансовый журнал. `presentation` работает со сценариями,
не выполняет SQL и не получает финансовые данные из внешних сервисов.

Длительные действия выполняются одним рабочим потоком. Сигналы принадлежат
GUI-владельцу, принимаются QObject-слотами в его потоке; там же вызываются и
освобождаются callback. Завершение ждёт выхода QRunnable до удаления сигналов. На время действия кнопки блокируются, закрытие окна откладывается.
Внутри книги изменения сериализованы RLock. Второй процесс не открывает ту же
книгу одновременно: используется файловая блокировка вне каталога данных.

## Журнал этапа 4

`domain/ledger.py` задаёт виды операций, проводки и точные инварианты.
`application/ledger.py` принимает команды через протокол LedgerRepository.
SQL-адаптер сохраняет операцию, все проводки, версию, родителей, журнал и
квитанцию в одной транзакции. Исправление требует ожидаемой принятой версии;
удаление сохраняет tombstone. Остатки учитывают только принятые активные версии.

Русский интерфейс содержит журнал, формы ручного ввода, историю и остатки на
календарную дату. UI не вычисляет баланс. Значения вводятся через Money.parse,
форматируются из целых копеек; float не используется.

Новые книги dev10 имеют схему 0010. Книги 0002 открываются со справочниками, 0003 —
с обычным журналом, 0004 — с разделением, 0005 — с возвратами, 0006 — с закрытием месяцев без тегов и сохранённых фильтров; 0007 добавляет теги/условия,
0008 — локальный импорт, 0009 — правила категорий, 0010 — аудит OCR. Части дохода/расхода
формируют одну проводку актива и несколько проводок категорий; сумма частей
равна сумме операции. `domain/refunds.py` ограничивает связанные возвраты по
категориям и проверяет совместимость с текущей покупкой. Возврат хранит также
неизменяемую версию источника; новый запрос требует её актуальности.
Обновление 0002–0009 до 0010 выполняется только в промежуточной базе при восстановлении
проверенной копии в новую папку. Исходная книга не мигрируется.
`domain/periods.py` задаёт календарный месяц, `application/periods.py` — явные
команды закрытия/открытия. SQL-адаптер хранит причины и версии в общем журнале.
Запись операции проверяет новый и прежний месяц внутри той же транзакции;
SQL-триггер независимо запрещает запечатывание в закрытом месяце.
Закрытие и запись сериализованы общим RLock.
Сверка через `Ledger.reconcile` читает согласованный снимок остатка и операций
в одной транзакции, сравнивает точные целые значения. Предметное правило
находится в `domain/reconciliation.py`; UI показывает разницу и не пишет данных.
Она доступна во всех схемах с журналом, включая 0003, без миграции.
`domain/query.py` задаёт переносимые условия журнала. Группы пересекаются,
значения внутри группы объединяются, выбранные теги требуются все. Счёт и банк
должны относиться к одной стороне перевода. Фильтр не участвует в расчёте остатков.
`application/organization.py` и SQL-адаптер хранят версии тегов/сохранённых фильтров
в общем журнале; назначения тегов принадлежат версии операции. Новые таблицы
доступны в 0007/0008/0009/0010, обычный фильтр — во всех схемах с финансовым журналом.
`domain/imports.py` отделяет исходную строку от исправленного OperationDraft.
Ограниченные локальные парсеры находятся в `infrastructure/importing`, сценарии
чтения/предпросмотра/подтверждения — в `application/importing.py`. SQL-адаптер
сохраняет ImportBatch/ImportItems и финансовые версии одной транзакцией/RLock.
Общий внутренний путь записи Ledger сохраняет прежние инварианты; проверка
итогового состояния выполняется после всех строк. Существующая операция может
получить связь с выпиской без новой финансовой версии. Исходный файл не копируется
в книгу, нормализованный аудит хранится в SQLCipher. Сетевой обмен аудита не реализован.
Для цепочки фоновых шагов callback вызывается после освобождения предыдущего Job.
Оставшиеся пункты приёмки этапа 3 перечислены в docs/stage-3-report.md.

Продолжение утверждённого плана разрешено пользователем 26.10.2026; это не
подменяет приёмку реализованных этапов и не разрешает менять стек/объём. OCR возвращает
черновики и не сохраняет факты. Рыночные цены изменяют оценки, а не сделки.
Синхронизация использует UUID, версии и журнал, но не копирование живой SQLite.

## Зафиксированные пользовательские решения

- Windows 11 x64.
- Российские акции, облигации и биржевые фонды.
- Котировки запрашиваются только кнопкой «Обновить цены».
- Все дополнения утверждены: сверка, CSV/OFX, возвраты, закрытие периодов,
  теги, сохранённые фильтры.
- Основная валюта RUB; Android Kotlin/Compose/Room.
- Полноценный OCR с типами A/B, Т-Банком, ВТБ и Яндекс Пэй остаётся обязательным.


## Управляемый экспорт журнала

`domain/exporting.py` задаёт неизменяемые условия/снимок/названия и формат CSV/JSON.
`SqlExportRepository` читает текущие финансовые версии и названия одной транзакцией
под RLock; `application/exporting.py` сохраняет именно просмотренный снимок
при открытой сессии той же книги. Экспорт не добавляет таблиц/версий/квитанций
и не меняет балансы. Доступен в 0003–0010 без обновления книги.

GUI выбирает условия и поля, показывает до 200 строк и общий состав, затем
пользователь выбирает новое имя файла. Файловый адаптер публикует завершённый
файл без замены существующего имени; временный файл удаляется только если
создан этим вызовом. Сохранение внутри папки книги запрещено. Предлагаемая
папка — LocalAppData/PersonalFinance/exports, отправки внешним сервисам нет.
[Формат](export-format-draft.md), [ADR-0009](adr/0009-journal-export.md).

## Правила категорий — 0.2.0.dev9

`domain/classification.py` отделяет вход без денег/финансовой команды от подсказки.
Неизменяемый снимок содержит правила и категории одной SQL-транзакции/RLock.
При импорте сопоставление всех строк выполняется в рабочем потоке; GUI получает
готовые решения и названия. Результат не меняет уже созданные факты.
`application/classification.py` проверяет открытую сессию; SQL-адаптер сохраняет
правила как kind=category_rule с общей историей и квитанциями. Включение —
неудалённая версия, выключение — is_deleted. Доступно в 0009/0010; старые книги не
обновляются при открытии. Миграция сохраняет точные определения прежних триггеров
в той же транзакции и добавляет отдельные защиты правил.
[Контракт](classification-rules-draft.md), [ADR-0010](adr/0010-category-rules.md).


## Первый технический срез OCR

В stage-5-ocr domain/ocr.py задаёт неизменяемые вход/слова/области/результат
без Qt/SQL/процессов. application/ocr.py использует порт OcrEngine и проверяет
принадлежность ответа входу; открытая книга для этого не нужна.
infrastructure/ocr/images.py нормализует PNG/JPEG через уже имеющийся Qt,
tsv.py строго разбирает слова, tesseract.py проверяет локальный комплект и
вызывает ограниченный процесс из process.py. Каналы остаются в памяти.
Опытные A/B Т-Банка и окна проверки полей добавлены следующим срезом ниже.
Этот первый срез не включал финансовое подтверждение; текущий dev10 описан ниже.
Поставка runtime остаётся незавершённой.
Runtime кандидата в EXE не включён. [Контракт](contracts.md#локальный-ocr--первый-технический-срез-этапа-5),
[результаты](stage-5-ocr-report.md).


## Опытная проверка OCR-полей

domain/ocr_cards.py хранит предложения, происхождение и ручную проверку;
application/ocr_cards.py оркестрирует порты. t_bank.py/t_bank_history.py и
vtb.py/vtb_history.py отделяют тип A от B; банк выбирается явно. rub_fields.py
разбирает общие точные поля, rows.py сохраняет индексы исходных слов.
Qt остаётся в infrastructure/presentation.
ocr_preview.py показывает источник/поля, ocr_history.py — выбор строки.
MainWindow получает tuple профилей CardRecognition; обычный bootstrap
оставляет его пустым. bank_name передаётся до дочерней карточки.
tools/preview_ocr.py внедряет локальный комплект по закреплённому
манифесту репозитория. Окно открывается после завершения Job. Проверка полей
сама не создаёт финансовых команд; отдельный путь dev10 описан ниже.
[Опытный запуск](windows-quickstart.md#опытная-проверка-ocr--этап-5),
[результаты](stage-5-vtb-report.md).

## Подтверждение OCR — dev10 / 0010

`domain/ocr_imports.py` задаёт каноническое происхождение выбранной строки,
OcrSelection и статусы повторов без Qt/SQL. `application/ocr_importing.py`
проверяет принадлежность ручного результата предложению. `SqlOcrRepository`
использует прежний внутренний путь Ledger и общий RLock: новая операция/связь,
квитанция и append-only ocr_records записываются одной транзакцией.

`ocr_confirmation.py` разделяет явный вид/счета/категории и последнее подтверждение;
MainWindow запускает preview/confirm в рабочих Job, освобождая предыдущий Job
до открытия следующего окна. Обычный bootstrap по-прежнему не внедряет OCR-профили.
Старая книга не мигрируется и не получает этот финансовый путь.
[Контракт](ocr-confirmation-contract.md), [ADR-0012](adr/0012-ocr-confirmation.md).
