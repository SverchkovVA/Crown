# Предложение: хранение универсального OCR

29.10.2026. Статус: проект для отдельного согласования. Не реализовано и не запускалось.
Текущая версия dev13 использует схему 0011 и универсальный предпросмотр без записи.

## Причина

ck_ocr_flags в миграции 0010 разрешает только bank IN ('Т-Банк','ВТБ').
Декодер канонического JSON в domain/ocr_imports.py также проверяет эти два
профиля и соответствующий префикс адаптера. Новый разбор «Любой банк» нельзя
выдать за один из них: происхождение записи станет недостоверным.

## Предлагаемое изменение

После согласования добавить новую миграцию 0012, расширяющую только список
профилей до Т-Банк/ВТБ/«Любой банк». Прочие части ck_ocr_flags, STRICT,
первичные/внешние/уникальные ключи, индексы и все триггеры 0010/0011 сохраняются.
Декодер сможет принимать generic-* только с новым профилем. Значения bank
старого аудита, канонический JSON версии 1, хеши доказательств/команд, UUID,
порядок строк и квитанции не переписываются. Слово «банк» в прежнем поле
останется историческим именем профиля разбора, не доказательством подлинности.

До: bank IN ('Т-Банк','ВТБ'). После: bank IN ('Т-Банк','ВТБ','Любой банк').
Это описание ожидаемой разницы, не готовый SQL-скрипт для пользовательской базы.
SQLite не меняет CHECK на месте: потребуется пересоздание таблицы с переносом
строк и точным восстановлением связанных SQL-объектов. Поэтому одного изменения
списка в Python недостаточно; нельзя редактировать старую миграцию 0010.

## Переход и проверяемые условия

1. Исходные старые книги открывать без миграции; перед переходом закрыть приложение,
   сделать отдельную копию всей папки и проверенную зашифрованную резервную копию.
2. Миграцию выполнять только в промежуточной базе восстановления. Результат
   публиковать только в новую папку после проверки SQLCipher/FK/истории/аудита.
   Новые книги после принятия изменения создаются сразу с новой схемой.
3. До любых пользовательских переходов проверить на вымышленных книгах все
   строки/байтовые payload/хеши, сохранность индексов/триггеров/STRICT, FK,
   неизменяемость/повторы/пересечения и отказ неизвестного профиля/неверного префикса.
4. Искусственно прервать DDL/копирование/восстановление защит: операция обязана
   откатиться полностью; исходная база, ключевой файл и контейнер остаются прежними.
5. Проверить совместимость чтения 0010/0011, переход цепочки старых копий,
   повтор пакета после восстановления, смену реплики, источник с другим DPI и
   возможные совпадения. Все строки общего списка записывать одной транзакцией
   через существующий Ledger/OcrImporting, с теми же финансовыми инвариантами.
6. Только после успешных локальных проверок Windows PowerShell 5.1, Linux/Windows
   CI и самопроверок source/EXE подключить финансовую кнопку общего профиля.
   Предыдущая версия, не знающая 0012, должна явно отказать при её открытии.

Риски: потерянный триггер/индекс, неполный перенос аудита, несовместимость старого
приложения, частичная публикация восстановленной папки. Эти риски требуют
отдельных проверок миграции; успешный предпросмотр их не закрывает.

## Почему требуется решение пользователя

Автоматическая проверка разрешений отклонила попытку изменения схемы 0011→0012
и пересоздания таблицы/защит как изменение хранения с риском для существующих
книг за пределами явно разрешённого универсального распознавания. Команда не
была выполнена. Изменение не обходилось: dev13 ограничен режимом без записи.
Этот документ делает следующий шаг конкретным и доступным для проверки.
