# Копии и восстановление

## Процедура пользователя

1. Откройте книгу → «Защита и копии» → «Создать зашифрованную копию».
2. Выберите новое имя файла за пределами папки книги и отдельную парольную фразу.
3. Дождитесь сообщения о завершении проверки.
4. Храните хотя бы одну копию на другом физическом носителе.
5. Для восстановления выберите файл, пароль копии, новую папку и новый пароль книги.
6. Сохраните новый код восстановления и проверьте справочники, операции и остатки.

Существующая папка книги и существующий файл копии не заменяются. Проверка копии
не создаёт восстановленную книгу. Повреждение/неверный пароль не публикует новую
книгу. Восстановление можно проверять, сохраняя исходную книгу.

В диалоге открытия полный код `PF1-…` автоматически включает режим
«Использовать код восстановления». В 0.1.1 флажок нужно включать вручную.
В одном ручном сценарии 0.1.2 автоматический выбор не сработал, но с ручным
флажком код открыл книгу; причина ещё не установлена. Парольная фраза книги
и код восстановления — разные способы доступа.
После восстановления копии используется новый код, показанный для новой книги.

Код восстановления помогает открыть сохранённую книгу при потере пароля. Он не
содержит финансовую историю: при утрате файлов книги нужна резервная копия.

## Формат v1

Фиксированная сигнатура PFBAK, ограниченный по размеру JSON-заголовок, Argon2id и
libsodium secretstream XChaCha20-Poly1305. Заголовок включён как дополнительные
аутентифицируемые данные каждого блока.

Первый шифрованный блок: UUID книги, ключ внутреннего SQLCipher-снимка, размер,
SHA-256, версия схемы и время UTC. Далее идут блоки снимка до 1 MiB и обязательный
пустой TAG_FINAL. Дополнительные байты, перестановка, изменение или обрыв блоков
не принимаются. Предельный размер базы этой версии — 10 GiB.

Полученный SQLCipher-снимок проверяется до упаковки. Готовый контейнер повторно
полностью читается до публикации имени. Файлы закрепляются fsync; на POSIX также
fsync каталогов. Поведение накопителя и реальные сбои питания на Windows ещё
требуют отдельного испытания.

При восстановлении все блоки проверяются в промежуточной папке. Проверяются
SQLCipher, схема, связи и история. История реплик сохраняется, но local_state
получает новую реплику, предотвращая повторное использование её последовательности.

## Переход с 0.1.2 на журнал

Версия 0.2.0.dev9 поддерживает чтение книг и копий схем 0002/0003/0004/0005/0006/0007/0008/0009. Копия хранит
фактическую схему исходной книги. Открытие старой книги не обновляет её: для
0002 доступны справочники и резервирование, для 0003 — обычный журнал без частей, для 0004 — разделение без возвратов, для 0005 — возвраты без закрытия периодов, для 0006 — закрытые месяцы без тегов/сохранённых фильтров, для 0007 — теги/фильтры без импорта, для 0008 — импорт/экспорт без правил.
Для функций текущей схемы создайте и проверьте копию, восстановите её в новую
папку новым паролем и сохраните новый
PF1. Миграция 0002/0003/0004/0005/0006/0007/0008 → 0009 выполняется только в промежуточной восстановленной
базе. Исходная 0002 остаётся совместима с 0.1.2, 0003 — с 0.2.0.dev1. Книгу
0004 открывает 0.2.0.dev2, 0005 — 0.2.0.dev3, 0006 — 0.2.0.dev4/0.2.0.dev5, 0007 — 0.2.0.dev6, 0008 — 0.2.0.dev7/0.2.0.dev8, новую 0009 — 0.2.0.dev9; обратного преобразования схем нет. Контейнер и формат
ключей остаются v1. Закрытые месяцы и вся история причин сохраняются
после восстановления; восстановление не открывает периоды автоматически.
Теги, их назначения, архив и версии сохранённых фильтров переносятся с теми же UUID.
История подтверждённого импорта и ключи повторов переносятся с теми же UUID;
новая реплика не разрешает повторно создать уже импортированную операцию.
Для обычного фильтра и сверки в старой книге с журналом миграция не требуется.

Автоматическая ротация, расписание копий, вложения и предварительный просмотр
состава восстановления появятся позже. Пользовательские копии сейчас вообще
не удаляются приложением. Папка текущей книги не является резервной копией.

Правила 0009 и их включённые/выключенные версии входят в тот же SQLCipher-снимок.
Восстановление сохраняет историю и решения правил, меняет локальную реплику.
Переход 0008 → 0009 проверяется с неизменностью SHA-256 исходной базы и key.json
на синтетической книге; никаких пользовательских ключевых файлов тесты не читают.
